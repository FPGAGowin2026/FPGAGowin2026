# 赛题 FPGA 部分实施规划（讨论稿）

更新：2026-09-24。依据本次提供的赛题截图及当前工作区制定。本文以赛题基础任务的 FPGA＋软核 CPU 实现为主，并标明拓展任务和后续 SLAM 的接口；摄像头识别等拓展功能尚未排入基础实施阶段。本文是待标定和验证的实施方案，不表示模块已经上板。已有[系统总体方案](系统总体方案.md)按 Jetson 承担导航/EKF 编写；针对本次赛题的 FPGA 独立基础任务，以本文的职责划分为准，后续整机方案需再同步调整。

## 1. 目标和边界

赛题基础任务要求仅用 FPGA＋软核 CPU 完成：①摄像头采集和图像显示、IMU 姿态采集与显示；②前进、后退、转向、定点旋转及带编码器反馈的闭环控制；③测距、障碍检测、自动减速、自动停车和自主避障；④起点到终点移动、障碍绕过及路径点导航。评分重点为 FPGA 实时感知与控制 40%、系统稳定性 25%、自主导航 20%、创新设计 10%、AI 扩展 5%。

本方案采用现有 ACG720-60K、四轮麦轮、AT8236、四轮编码器、IMU660RC（LSM6DSV16XTR，SPI）、**2D 激光雷达**、OV5640、板载 DDR3 和 TFT。总体定位使用 IMU、2D 雷达和轮速计；首版 EKF 先融合 IMU 与轮速，雷达校正及后续 SLAM 按地图来源选择接入方式。雷达具体型号/输出格式、实际接线、采样率及场地条件尚未固定。板卡资源、管脚和功耗以整机综合及实物为准。按赛题截图，扩展任务允许 RK3588 等边缘 AI 平台；该平台不进入基础任务的控制、避障和导航闭环。

**主线定位：** FPGA 是实时反射层。可并行完成采集、预处理、局部状态估计和电机控制；检测到近障碍、失联或故障后，硬件直接约束运动。软核负责低频初始化、参数、地图或路径点管理和局部导航决策，不能绕过最终运动仲裁直接写电机 PWM。

### 已讨论模块与赛题任务的对应关系

| 内容 | 对应要求 | 本方案中的作用与边界 |
|---|---|---|
| OV5640 采集、DDR3 帧缓存、TFT 画面显示；IMU 采集与姿态显示 | 基础任务 1：多传感器感知 | 完成摄像头画面和姿态信息的实时显示；显示画面不等于视觉目标识别 |

| 后续 2D 雷达 SLAM | 支撑基础任务 4，也可体现创新设计 | 场地条件需要时建图与全局校正；赛题截图未明确要求完整 SLAM 或回环优化 |
| OV5640 目标检测/识别 | 拓展任务 5：视觉目标识别 | 识别人员、物体或指定目标；仅将视觉特征加入 EKF 不等于完成该任务 |
| 基于识别结果的搜索、靠近、任务执行 | 拓展任务 6：智能任务执行 | 将识别结果、导航和运动控制连成可演示任务；单有运动控制或识别模块不算完成 |

评分项与任务并非一一对应：FPGA 实时感知与控制占 40%，要在任务 1～3 的采集、保护和闭环中体现；系统稳定性占 25%，需在整机长时运行与故障恢复中验证；自主导航占 20%，主要由任务 4 验证；创新设计占 10%，AI 扩展占 5%。功能实现和评分效果都以现场测试为准。

## 2. 功能分层与数据流

```text
OV5640 ──采集/帧缓存────────────────────────────→ TFT 图像/姿态/状态显示
四轮编码器 ──QEP/测速/FK ─┬─→ 四轮速度 PI 反馈
                         └─→ 时间对齐/异常标记 ─┐
IMU660RC ──SPI/标定/去偏/时间戳 ─────────────────┼─→ FPGA 定点 EKF ─→ 局部位姿/质量
2D 雷达 ──逐点解析/时间戳/过滤 ─┬─→ 扫描匹配/位姿观测 ─┘       │
                              ├─→ 近距直通保护 ─────────────┤
                              └─→ 局部障碍数据/软核导航 ←────┘
软核路径点/速度请求 ─→ 指令有效性/运动仲裁/限速 ─→ 麦轮 IK ─→ PI×4 ─→ 输出门控 ─→ AT8236
```

雷达原始距离点不直接作为二维位姿量塞进 EKF：先完成扫描匹配或特征定位，得到带时间戳、匹配质量和不确定度的位姿观测，再决定是否校正。原始距离点同时供近距保护与局部导航使用。摄像头链路先完成赛题要求的采集显示，不把图像识别或视觉里程计放入基础任务的必经链路。显示和数据上传拥塞不能反压电机控制与近距保护。

| 层级 | FPGA 硬件 RTL | 软核 CPU |
|---|---|---|
| 传感器 | SPI、编码器、雷达接口、相机采集；逐点解析、校验、时间戳、过滤与有效性 | 初始化、参数配置、慢速诊断 |
| 状态估计 | 固定周期定点 EKF、异常数据拒绝、状态与质量输出；按资源评估雷达前端加速 | 雷达扫描匹配/局部地图的首版原型、噪声参数与调试记录；通过实测决定软核和 RTL 分工 |

| 显示 | OV5640→DDR3→TFT、姿态与故障叠加 | 低速显示配置 |

### 麦轮正、逆运动学：基础任务 2 到任务 4 的接口

当前 RTL 约定轮序为左前 `FL`、右前 `FR`、左后 `RL`、右后 `RR`，车体系 `x` 向前、`y` 向左、`ω` 逆时针为正，适用于已假定的 X 型麦轮安装。设 `L = 半轴距＋半轮距`，`u` 为轮缘线速度，则逆运动学把导航或调试给出的车体速度变成四轮目标：

```text
u_FL = v_x - v_y - L·ω       u_FR = v_x + v_y + L·ω
u_RL = v_x + v_y - L·ω       u_RR = v_x - v_y + L·ω
```

正运动学使用**编码器测得的**四轮速度，反算送往里程计/EKF 的车体速度：

```text
v_x = (u_FL + u_FR + u_RL + u_RR) / 4
v_y = (-u_FL + u_FR + u_RL - u_RR) / 4
ω   = (-u_FL + u_FR - u_RL + u_RR) / (4L)
```

RTL 接口使用 `v_x/v_y` 的 mm/s、`ω` 的 mrad/s，因此旋转项实际计算为 `L·ω/1000`，正运动学的角速度输出再乘 1000。若需要轮子角速度，用轮缘线速度除以**有效轮半径**。当前参数文件的轮径 80 mm 是规格参考，轴距 180 mm、轮距 200 mm 为估值，故 `L=190 mm` 也只是原型值；编码器每轮一圈的有效计数、轮位映射及电机/编码器正反极性均未实车确认。[RTL 实现](../FPGA_ws/rtl/motor/mecanum_motor_control.sv)与[板级参数](../FPGA_ws/boards/acg720_60k_motor_closed_loop/motor_closed_loop_config.sv)须按接线和标定同步更新。

上板先逐轮确认轮位、正向与编码器计数方向，再分别验证前进、左横移和逆时针原地旋转的四轮符号；例如 `v_y=+100 mm/s`、其他指令为零时，目标应为 `FL=-100、FR=+100、RL=+100、RR=-100 mm/s`。随后用实测每圈计数与有效轮径标定测速比例，验证组合运动、四轮限速/斜坡和闭环跟踪。麦轮横移可能打滑，正运动学结果是轮式里程计估计，进入 EKF 时须依据实测横移/旋转误差设置不确定度。

## 3. EKF 的最小可实现范围

第一版先实现**IMU＋轮速计局部 EKF**，同时保留固定地图模式下的 2D 雷达观测更新接口，最终形成所规划的三源定位链。建议从 `x = [p_x, p_y, ψ, b_g]^T` 的四状态模型起步：局部位置、相对航向和陀螺仪 z 轴零偏。四轮编码器经麦轮 FK 得到车体系 `v_x/v_y/ω_w`；IMU 提供 `ω_g`。预测使用轮式平移速度、去偏陀螺角速度和采样间隔；在固定地图模式中，雷达扫描匹配形成 `p_x/p_y/ψ` 观测，质量合格且相关性得到处理时才校正预测状态。轮式角速度可辅助零偏估计。若四状态模型在真实数据中不能满足运动状态质量需求，再评估把 `v_x/v_y` 纳入状态，而不是预先扩大矩阵。静止时可另做零速/零角速度约束，但必须判定确实静止。轮速和轮式角速度来自同一组编码器，陀螺数据也可能参与多处计算；参考模型必须处理这些相关性，不能把重复使用的测量按独立信息计算。

这一路会输出 `p_x/p_y/ψ`、车体速度、协方差或质量指标、时间戳及有效性。IMU 的横滚/俯仰姿态显示另由加速度计和陀螺仪的轻量估计完成；六轴 IMU 的航向只标为相对航向。雷达扫描匹配必须说明参照：**对已知固定地图或标志点匹配**可以提供地图坐标系下的校正；**仅做相邻扫描匹配**得到的是相对运动，仍可能积累漂移，不能直接宣称全局定位。若地图由同一融合位姿不断写入，再拿它当完全独立的 EKF 观测，可能重复计入信息；首版应记录地图来源与更新时机，并用离线回放检查一致性。

雷达前端另设独立可行性门槛：选定雷达后记录点数、扫描频率、点级时间信息和接口吞吐；用采集数据比较扫描到固定地图或局部子图的匹配耗时、误匹配率和有效区域。先在软件参考中实现并测软核运算预算；不足时再挑选过滤、特征提取或匹配评分热点做 RTL 加速。不得在未验证扫描匹配可实时运行前，将“雷达参与 EKF”视作完成。外参标定、时钟对齐、扫描运动畸变和走廊等几何退化场景必须纳入测试。

实现顺序：先建立双精度软件参考与传感器记录回放，再确定状态/过程噪声/观测噪声；随后建立与 RTL 相同舍入和饱和规则的定点模型；最后实现可复用乘加、顺序矩阵运算、三角函数查表或 CORDIC 的 RTL。矩阵维度保持固定，不做通用矩阵加速器。每轮更新须在下一采样周期前完成，并检查溢出、协方差对称性与正定性、静止漂移、转弯及横移误差。资源或数值误差超出预算时，先缩小状态与更新频率，再评估其他实现分配；不得让 EKF 阻塞近距保护。

## 4. 实时反射与自主导航

**快速保护链：** 雷达点接收后做协议/量程/时效检查；有效近距结果直接触发限速或停车，不等待扫描匹配、EKF、软核或整帧地图更新。障碍方向至少区分前、后、左、右，并考虑麦轮横移与原地旋转。保护阈值由雷达扫描/传输延迟、车辆外形、实际制动能力和余量决定。无效或过期数据不能当作“无障碍”。2D 扫描平面之外的低矮/悬空障碍是覆盖边界；是否补充 ToF 由实测决定。驱动失能是否制动、是否滑行须实测。

**软核导航链：** 从赛题场地出发，先实现固定路径点序列、融合位姿到点判断和速度请求；再加入雷达局部障碍触发的停等/绕行、回到路径和超时退出。若场地未知且要求在线建图，评估现有 N10/2D 雷达资料能否在 60K＋软核上完成扫描匹配、局部地图和定位；赛题未要求的完整 SLAM 和回环优化不预设为基础任务。起终点、路径点精度、障碍尺寸和是否需要在线建图应以完整赛题规则及场地实测冻结。

### SLAM 是否进入 FPGA 基础任务

赛题截图要求自主导航和避障，没有明确要求建图或回环优化。以下按场地条件决定，不把“雷达参与 EKF”等同于“必须实现完整 SLAM”：

| 场地条件 | 建议实现 | 是否需要完整 SLAM |
|---|---|---|
| 已知场地或允许预先测绘 | 雷达对固定地图/标志点匹配，输出位姿给 EKF；软核按路径点导航 | 不需要在线建图 |
| 未知但路线短、障碍可局部绕行 | 扫描匹配、滚动局部地图和路径点跟踪；记录累计漂移并限定可用距离 | 先不做回环优化 |
| 未知且路线长、存在重复经过或严格全局到点要求 | 在线建图、重定位及可能的回环校正 | 需另立资源和精度验证阶段 |

若进入第三种情况，优先由 FPGA 硬件做雷达解析、时间戳、过滤和保护；软核试做有界地图与匹配，仅将实测瓶颈搬到 RTL 加速。必须把软核、EKF、相机/DDR3 和电机链路放在同一 60K 工程中测资源与时序，再决定完整 SLAM 是否现实。

### 后续雷达 SLAM 的接口预留

既然后续计划用 2D 雷达做 SLAM，首版 EKF 就预留两套坐标：`odom` 是连续的局部里程计坐标，`map` 是建图和全局导航坐标。FPGA EKF 输出带采样时间、位姿、协方差/质量和序号的 `T_odom_base`；雷达前端输出带点级或整帧时间信息、有效性和安装外参的扫描数据。SLAM 用扫描与里程计先验做局部匹配、子图更新及后续回环，输出 `T_map_odom`；导航所需全局位姿按 `T_map_base = T_map_odom × T_odom_base` 计算。回环可改变 `T_map_odom`，但不能让电机闭环使用的 `T_odom_base` 突然跳变。

这一阶段建议让 FPGA EKF 首先融合轮速和 IMU，提供高频连续的运动先验；雷达同时服务于近障保护和 SLAM。若还要把雷达匹配结果送回 EKF，必须明确匹配参照地图、时间和与 EKF 先验的相关性，不能把已经使用 EKF 先验生成的 SLAM 位姿当成独立观测再次融合。已有固定地图且匹配观测可独立建模时，可验证雷达校正的 EKF 分支；在线建图首版优先采用单向 `EKF → SLAM → map/odom 修正`，避免形成未处理相关性的反馈环。

60K 上先测完整工程的资源/时序，再用选定雷达的实测数据评估每帧扫描匹配、子图插入、地图存储及回环耗时。轻量局部建图可在软核上做有界原型；若完整 SLAM 超出软核预算，应将建图/回环安排在后续独立计算平台，并保留 FPGA 的采集、时间戳、保护、EKF 和控制职责。若 SLAM 被列为赛题基础任务，则必须按“FPGA＋软核 CPU”限制重新验证部署方案，不能用扩展任务允许的边缘 AI 平台代替基础任务实现。

### OV5640 在三源定位方案中的职责

OV5640 保留为独立视觉链路，首先完成赛题要求的**摄像头实时画面＋IMU 姿态显示**。在 TFT 上叠加相对航向、EKF 局部位置/质量、雷达近障方向、轮速与故障状态，能直接展示 FPGA 对多路传感器的同步处理；画面或显示失效不影响雷达保护及电机闭环。

完成基础显示后，再选一个与场地有关、可验证的轻量视觉功能，例如 RGB565 像素流中的彩色路标区域提取、区域中心/面积统计或地面引导线偏差。此类处理可在采集流上流水实现，只输出少量特征给软核；应记录光照变化和误检，不因示例画面成功就把它列为可靠定位源。

视觉可以作为 EKF 的**第四类观测**，但输入必须是带时间和不确定度的几何量，而不是原始图像。建议从场地中位置已知、身份可区分的路标开始：检测其图像中心，经相机内参换算为方位角，向四状态 EKF 提供“对已知路标的方位”观测。单个方位观测只约束部分位姿，仍须依靠运动和其他传感器。若能稳定检测已知尺寸标志的角点，再评估解算相机位姿、转换到车体/地图坐标并输入 `p_x/p_y/ψ`。单纯颜色区域中心不能推出距离或完整位姿；普通单目视觉里程计还有尺度歧义，不作为第一版四源融合的前提。

视觉观测进入 EKF 前须完成相机内参、相机到车体外参、路标地图位置、采集时刻与处理延迟标定，并输出检测置信度/协方差；遮挡、误识别、过期画面和新息检验失败时跳过该次更新。先通过记录回放比较“三源 EKF”和“四源 EKF”在横移、旋转及雷达退化场景中的误差，再决定是否长期启用。基础近距保护继续依赖 2D 雷达及必要的盲区补充传感器。当前只有独立 OV5640→DDR3→TFT 参考工程和采集模块，尚无当前整机上板画面证据。

软核每次输出有时效的 `v_x/v_y/ω` 请求；硬件仲裁器根据近障碍、传感器有效性、故障和速度上限生成允许命令。通信或软核停顿时，电机控制不沿用无限期的旧请求。故障恢复需要新鲜命令；具体制动与重新使能动作以驱动和底盘实验确定。软核、DDR3 显示、网络、EKF 和四轮闭环合并后须做 60K 的资源与时序检查；若装不下，先简化地图规模、EKF 维度及非关键显示功能，再按赛题允许板卡评估迁移，不能仅凭单模块综合成功宣称整机可行。

## 5. 阶段计划与验收证据

| 阶段 | 主要工作 | 可签收证据 |
|---|---|---|
| A. 赛题与硬件基线 | 冻结基础任务演示口径、场地、2D 雷达型号/接口/扫描率及 IMU 率；核对 60K 管脚、电平、AT8236 真值表和供电 | 接线表、雷达数据格式、场地与验收指标表 |
| B. 现有四轮闭环上板 | 实测轮序、极性、每圈计数、轮径与几何；核对逆运动学四轮符号、正运动学反算和限速/斜坡；逐轮整定 PI，验证前后/横移/旋转 | 四轮目标与实测速度、正运动学输出、PWM、电流、停车记录；实际动作视频 |
| C. 传感器与显示 | IMU660RC SPI、时间戳和标定；2D 雷达逐点接入；OV5640→DDR3→TFT 分段接通 | IMU 静止/定轴数据、雷达扫描/年龄日志、TFT 彩条→相机→姿态叠加视频 |
| D. 雷达定位与 EKF | 先做 IMU＋轮速双源参考和定点 RTL；验证固定地图下的雷达匹配、外参和时间对齐后，再加入三源校正分支与回放对照 | 双源/三源误差、匹配成功率与耗时、溢出与失效测试、板上更新耗时、资源及 STA 报告 |
| E. 实时反射 | 雷达近距减速/停车、方向约束、指令超时、仲裁和输出门控 | 近障碍、雷达过期、断链与恢复注入；实测响应时间和停车距离 |
| F. 软核导航 | 融合位姿下路径点到点、雷达障碍绕行和重回路线；按场地决定地图范围 | 起终点、多个路径点、障碍绕过的重复实验和轨迹/故障日志 |
| G. 整机收口 | 合并相机、DDR3、EKF、导航和四轮控制，复测时序/资源/长时运行 | 单一 60K 工程、码流哈希、P&R/STA、赛题任务 1～4 逐项演示 |

阶段 B、C 的无电机传感器部分和 D 的软件参考可并行；D 的 RTL 依赖有效的编码器/IMU/雷达数据、扫描匹配可行性和定点模型；E 的初版可先用雷达近距直通保护实施，不必等 EKF 完成。每一阶段分别标注“软件仿真、综合、板测、实车”证据，不能把其中一种代替另一种。

## 6. 当前起点与待决定事项

当前已有四轮麦轮 IK/FK、QEP/测速/PI 和 AT8236 的仿真与 ACG720-60K 离线构建；实际线束、轮位、极性、计数、闭环和制动尚未实测。IMU660RC 驱动、2D 雷达整机接入与扫描匹配、EKF RTL、雷达反射链、60K 整机导航及摄像头主线集成尚未完成。OV5640→DDR3→TFT 有独立参考工程，但不能当作当前整机板测结果。旧 N10 实验保留，不能直接算作本赛题导航完成。

下一轮最需要确定：①2D 雷达型号、安装高度、接口、扫描格式和频率；②场地尺寸、障碍形式、路径点/到点精度、是否提供地图或要求在线建图；③四轮接线及供电；④ IMU 的数据就绪脚、安装方向和目标输出数据率。确定后才能冻结扫描匹配方案、EKF 频率、定点位宽、延迟预算、资源上限和各阶段的数值验收门槛。

参考实现与接口边界可对照 [Cartographer 2D 局部轨迹构建](https://google-cartographer.github.io/cartographer/mapping/internal/2d/local_trajectory_builder_2d.html)和 [robot_localization 状态估计接口](https://docs.ros.org/en/noetic/api/robot_localization/html/index.html)；这里只借鉴扫描匹配到位姿观测的分层方式，不把这些软件包纳入 FPGA 工程。
